# V0.6/S1 容量基线与诊断结果

状态：**测量设施与有界诊断交付PASS；Gateway本体最大容量归因及S2入口BLOCKED。** 两角色各72项正式矩阵已完成，共3,859,200个正式请求。依据[Reviewer001](../../reviewer/reports/V0.6/S1-report-001.md)与[Leader003](../../leader/reports/V0.6/S1-report-003.md)收口；没有产品代码优化或发布。

## 环境与可比边界

Linux WSL2 6.6.87.2、Intel Core i5-13500HX、20个可用逻辑CPU，WSL可见内存约7.6GiB，Release构建。各测试进程继承CPU 0–19，未设置独立CPU配额或绑核；结果是同机拓扑观察，不是严格同CPU配额的横向扩容证明。E0的cgroup CPU/内存上限入口未取得值，不能据此推定无限配额。两仓实际源码/dirty diff和二进制指纹均记录，L4用户工作树只读；产品C++、旧工具与CMake没有修改。

| 路径 | 链路 | 聚合代理预算 |
|---|---|---|
| B | 客户端→模拟后端 | 无代理准入层 |
| G | 客户端→单Gateway→后端 | 32连接/准入，512MiB逻辑预约，4MiB流缓冲 |
| M | 客户端轮转→双Gateway→后端 | 总额同G，每实例各半 |
| L | 客户端→用户态TCP L4LB→双Gateway→后端 | Gateway总额同M，额外L4进程单独计资源 |

后端均为一个独立asyncio进程；每条流预约256KiB，因此主曲线聚合4MiB只允许16份流预约。32连接/准入不意味着32条同时流。逻辑预约不等于RSS实际分配。A为1024B JSON，S为16KiB SSE、16段、2ms目标间隔；含唯一ID及完整正文校验，不是模型推理或token负载。

每请求新下游TCP，上游复用关闭、队列为0。A使用两个发压进程、S使用一个，总槽数均128；单/双Gateway的全部配套额度按聚合预算比较。工具按开环scheduled时间发送，迟到或无槽保留not_sent，不追赶补发。

## 冻结方法与指标

每角色72项=2负载×4路径×3档×3重复，每点3秒预热、20秒正式、请求排空最多5秒，随后FD确认最多2秒，全部活动受45秒上限约束。每角色正式计划1,929,600请求，含预热共2,219,040请求。角色之间串行采集，重复内按路径轮转；不合池计算分位或挑选最优重复。

达标要求每次重复均满足：全部正式计划中SLO成功比例≥99%，生成器not_sent≤1%、dispatch lag P95≤5ms，无正文/协议/ID损坏，资源排空。A要求scheduled到HTTP完成≤100ms；S要求≤250ms且首body≤50ms。HTTP完成是完整framing解析完成的观测时刻，success还必须经过后续EOF和正文校验；后续校验CPU不计入HTTP时延。冻结清单的自然语言短句对此不够精确，勘误见[Leader启动及执行记录](../../leader/reports/V0.6/S1-report-002.md)，数字门槛与实际测量未变。

goodput=正式窗口内scheduled、最终在自身SLO内成功的请求数/20秒，包含窗口结束后在排空期内达标完成的请求。拒绝、传输失败、漏发都留在分母。延迟分位只描述成功样本，不能替代总体达标率；P50/P95/P99分别要求至少20/100/1000个成功样本。CPU保存真实窗口、ticks及单tick误差，峰值是周期采样峰而非连续峰。

正式清单最新SHA256为`f059fc20bf38d0c7f333440d925f1ff70316cd19beac7769b5fdc9bc49018e9a`，见[清单](S1-manifest.json)。[附加诊断计划](S1-diagnostic-plan.json)在末两控制采集前冻结，不改变主矩阵。

## 控制与归因

S/G480仅将流缓冲4MiB改8MiB，Builder达标比例由约81.67%升至100%；保持4MiB而改变发压进程数仍约81.67%。Reviewer独立同一控制为81.25%→100%，进一步支持流缓冲配置限制，不是产品代码提速。A/G3840单发压接近一个忙核，改双发压后P95/P99变化超过预注册10%门槛，因此正式A使用匹配校准的双发压配置。

L的A3840退化在重复中出现，但高负载后端/发压CPU接近忙核阈值，且同机CPU未隔离。末两同5秒窗口控制只配套增加聚合连接/池/准入/预约额度32→64：Builder达标98.776%→98.984%，都未过99%，P95约5.572→5.622ms。不能据此宣称额度增加稳定解决问题，也不能把L路径表现等同Gateway本体处理上限。Reviewer反向64→32的达标率99.010%/98.875%，P95为11.323/5.496ms、P99为23.419/7.544ms；cap64尾延迟更差且跨角色结果不一致。该短窗配额控制未证明稳定收益。

上游复用和采样频率诊断见[瓶颈记录](S1-bottlenecks.md)。另有三次5000记录的工具微基准：序列化约2.20–2.22µs/条，序列化加页缓存写约2.66–2.67µs/条；它不包含网络、解帧与正文校验，不能代替端到端工具开销。环境有strace、无perf命令，本轮没有取得产品调用栈或分配热点证据，因此不将某个产品函数命名为已确认瓶颈。所有控制单列，既有复用功能、提高配置额度及改变工具资源的效果均不称为新增产品优化。

## 首停、修正与证据保留

Builder有三次正式采集首停，均非零退出并保留原始result、failed账本和版本清单。第7项漏解析多词L4结束理由；第18项窗口外资源读取权限错误缺乏细节；第33项记录到窗口外读取已完成请求的发压进程/proc/fd时尚未取得退出码。见[返工001](../../leader/reworks/V0.6/S1-rework-001.md)、[002](../../leader/reworks/V0.6/S1-rework-002.md)、[003](../../leader/reworks/V0.6/S1-rework-003.md)。Reviewer在自身第33项另有一次窗口外FileNotFoundError首停，按[返工004](../../leader/reworks/V0.6/S1-rework-004.md)统一同类退出读取异常的安全门槛，原33项不重发、首错保留。

前33项均经绑定原始指纹的派生复审及独立逐请求/资源复算，未重发；其余39项使用最终工具采集，窗口参数与产品二进制保持。最终v5仅对PermissionError/FileNotFoundError/ProcessLookupError，在实际测量窗口结束后的自有进程排空/清理阶段，无信号等待最多100ms及剩余cell期限，取得退出码才跳过退出样本；窗口内、控制器及仍活进程异常仍失败。Builder v4阶段实际出现两次窗口外确认，约1.16/1.43ms后取得exit0。两个角色原第33项低达标率都没有被修正抹去。Builder使用v1–v4采集，Reviewer使用v4–v5采集；主窗口参数、请求工具与产品保持，工具变更集中于审计/窗口外收口。附加诊断原计划的v4引用保留，Reviewer依返工004使用v5，数值参数与反向顺序保持。

Builder累计118cell、活动账本2285.345秒、约1.018GB证据，425个自有PID全部回收，最大分片1MiB；都在120cell/90min/2GiB/1GiB RSS/2048FD约束内。Reviewer累计83cell、活动账本1961.060秒、约915.70MB证据，326个自有PID全部回收，最大文件1MiB。两角色Release各21/21，最终工具负控19/19，Reviewer自写解析负控5/5；Reviewer自写审计全量复算自身72正式+7成功控制，以及此前Builder的恢复前缀，未以提交工具的汇总代替自身样本审计。历史报告001–005是中间状态；Builder测量交接见006，最终工具修正见[007](../../builder/reports/V0.6/S1-report-007.md)，以最终Reviewer/Leader结论为准。
